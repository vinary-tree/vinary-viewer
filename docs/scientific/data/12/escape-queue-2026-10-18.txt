==== H-ESC — pre-registered 2026-10-18, before any experiment ====
Observation: two Escapes sent in one burst (sendChord twice, no wait) after a typed digit leave the show running.
Mechanism hypothesised: vinary.input.events/escape-fx answers each Escape with [:dispatch <step>] — the step
(here :slides/digits-clear) is QUEUED behind events already in re-frame's queue. Both keydowns run before the
router's next-tick flush (the burst is delivered as consecutive input tasks), so the queue holds
[:input/escape :input/escape]; the first queues :slides/digits-clear AFTER the second Escape, the second sees the
digit still typed and queues another :slides/digits-clear; the show is never stopped.
Experiment E1 (cljs test build, real re-frame router, Node): app-db ← a running show (:fullscreen? false, so no
window effect) with [:ui :slides :digits] "2"; (rf/dispatch [:input/escape]) twice in the same tick; read app-db
after the queue drains (setTimeout 50 ms).
  P-E1a (H-ESC): [:ui :presentation] is STILL present and the digit is gone — the second Escape was spent on a step
         already taken.        Null: [:ui :presentation] is gone.
  P-E1b (control, both hypotheses): one Escape, drain, a second Escape, drain → [:ui :presentation] is gone.
Fix design (F1), applied only if P-E1a holds: escape-fx applies its step in Escape's OWN event — it returns the
step's {:db :fx} (the same pure fns the step events use: slides-overview-close-fx, the digits clear,
slides/clear-blank, slides-stop-fx; and the palette/find close handlers' db + fx) instead of dispatching it — so
consecutive Escapes, however queued, each see the previous one's result.
  P-F1a: E1 passes with F1 (the show ends after two queued Escapes; three would leave Vim's mode switch next).
  P-F1b: the smoke step that failed in C5-1 passes unchanged (it is the E2E negative control: it failed before F1).
