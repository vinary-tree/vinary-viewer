==== H-PAIRWORK-FIX — the fix, designed and pre-registered 2026-10-18 BEFORE it is written ====
Requirement. Same value as today's note-page-signature? on EVERY input (exact equivalence: no decision of any deck
may change), with every case of the H-PAIRWORK bench far below the long-task threshold. Target: each case's release
median ≤ 16 ms on this machine (core 3, governor performance), so that a 3× slower machine stays under 50 ms.
Design F (three changes, each proved equivalent):
  F-a  The visits that cannot match are never made. For a slide run of height hs, the kept note runs of its string
       are {k : 0 < h_k/hs ≤ max-thumbnail-scale} (h_k = run-height k > 0, upright?). With the string's runs sorted
       by height ascending, h ↦ h/hs is non-decreasing (IEEE division is monotone), so "h_k/hs ≤ 0" (underflow,
       or hs = +∞) holds on a prefix and "h_k/hs ≤ 0.4" on a longer prefix (NaN, from ∞/∞, only at the end):
       the kept runs are the index range [lo, hi), found by two binary searches. Cost per slide run O(log r_j).
  F-b  A counting pass first: total = Σ (hi − lo). Today's loop returns nil iff the TOTAL exceeds
       max-signature-matches (its cap check precedes the end test, and the count only grows); so nil iff total > cap,
       decided before a match is built. Otherwise the matches are built into preallocated typed arrays of exactly
       `total` entries: slide-run index i, and the three cell quotients ln σ / ln(1.02), tx/tol, ty/tol — each the
       same double today's code computes in every pass (same expressions on the same doubles).
  F-c  copy-covers? keeps its eight grids, its cell formula floor(q − shift) and its order-free verdict (true iff
       some grid has a cell whose DISTINCT slide runs carry ≥ need glyphs: sums only grow, so the early exit does not
       change the verdict). Cell keys: the three integers packed into one exact double when each lies in
       [−65535, 65535] ((a+2^16)·2^34 + (b+2^16)·2^17 + (c+2^16) < 2^51; −0 and 0 pack alike, as str prints both
       "0"), else today's string key (a number never equals a string in a js/Map: the encoding stays injective).
       The per-cell js/Set of slide runs becomes a per-cell "last slide run": matches come grouped by i in ascending
       order, so "i already in this cell" ⟺ "the cell's last run is i".
Predictions (release arm, the same bench, unchanged except that it now also times the fixed code):
  Q1 A(4096) ≤ 10 ms, B ≤ 10 ms, D ≤ 1 ms (medians).
  Q2 C ≤ 50 ms. If C > 16 ms, max-signature-matches is lowered to the largest power of two whose C median ≤ 16 ms,
     PROVIDED the census of real decks shows max matches ≤ cap/16 (a 16× margin); otherwise this stops and is
     reported. (Lowering the cap is the only change that could alter a result: nil for 16 384 < matches ≤ 65 536.)
  Q3 Equivalence, measured three ways: (E1) a property test — the fixed and a verbatim copy of today's
     implementation (a test-only reference namespace) agree on ≥ 20 000 generated pairs, generators covering repeated
     strings, σ at and around 0.4, underflow to 0, infinite heights, coordinates outside the packing range, and pairs
     around the match cap; (E2) the census pairs of every listed deck: zero disagreements; (E3) vv --cli --deck-info
     over experiment 13's 146 PDFs and the fixtures, before and after: identical lines.
  Q4 the unit build green; lint green; the full verification green before the commit.
Refuted (the fix rejected) if any disagreement is found (Q3), or if Q1/Q2 fail with the cap kept.

==== H-PAIRWORK-FIX′ — design F′, pre-registered 2026-10-18 BEFORE it is written ====
F-a and F-b are kept unchanged. F-c is replaced by F′-c; nothing in the comparison then hashes a cell with a hash
the PDF's author can predict:
  F′-c  copy-covers? keeps its eight grids, its cell formula ⌊q − s⌋ on the same precomputed quotients, its
        "last slide run" dedup and its order-free verdict. Its cells live in a hash table of its own, on typed
        arrays: B buckets (the least power of two ≥ 2m, at least 16), chaining (a head per bucket, a next per cell),
        a stamp per bucket so that each grid starts empty in O(1), and per cell its three indices, last slide run
        and sum. The hash is drawn AT RANDOM ON EVERY CALL from a universal family: with p = 2^31 − 1 (prime),
          in range (every index within ±65 535):  u = (α₀ d₀ + α₁ d₁ + α₂ d₂ + β) mod p,  dᵢ = indexᵢ + 65 536 < 2^17;
          otherwise:  u = (Σ γⱼ eⱼ + δ) mod p over the twelve 16-bit halves eⱼ of the three indices' canonical bits
          (−0 as +0; every NaN as one pattern);
        bucket = u mod B; α, β, γ, δ uniform in [0, p) from crypto.getRandomValues. Every product is below 2^48 and
        every sum below 2^53, so u is exact in doubles. For any two distinct cells, the chance that they share a
        bucket is at most 1/B + 1/p, whatever the input — the input is fixed before the hash is drawn — so the
        expected chain walked per match is at most 1 + m(1/B + 1/p) < 1.6. Cell equality is componentwise
        SameValueZero, which is exactly when today's string keys are equal (Number::toString is injective on
        doubles but for +0/−0, and NaN prints one way). The hash decides only where a cell is stored, never which
        matches share a cell, so the verdict does not depend on the draw.
  (by-height keeps the note page's string groups in a js/Map with string keys — V8's seeded string hash — unless the
  probe above shows array-index strings defeat it; then F′ groups the strings in a table of its own, seeded the same
  way over the strings' UTF-16 code units, and this registration is amended before that is written.)

  Q1′ release medians: A(4096) ≤ 10 ms, B ≤ 10 ms, D ≤ 1 ms.
  Q2′ release medians of C, C-rand, C-flood and C-far each ≤ 16 ms at the cap 65 536. Otherwise the cap is lowered to
      the largest power of two X ≥ 8 192 (the census's 16× rule: 16 × 372 = 5 952) for which C(X), C-rand(X),

==== H-PAIRWORK-FIX′ — AMENDMENT before F′ is written (2026-10-18): the hash family ====
Found while writing F′'s proofs, before any of F′'s code: the registered family u = (α·d + β) mod p is PAIRWISE
independent only. That bounds the expected chain (the registered < 1.6) for every input, but the TAIL only by Markov's
inequality — and the PDF's author controls the cells' structure exactly (an arithmetic progression of cells along one
axis is a row of note runs), and with B a power of two the bucket is u's low bits, where such structure survives for
the multipliers α with low bits zero. No bound beyond Markov is claimed for it, so it is replaced, before it is written,
by SIMPLE TABULATION [Carter–Wegman 1979; Pătraşcu–Thorup 2012]:
  F′-c (amended)  each of a cell's three indices is hashed by its CANONICAL 64 bits (−0 as +0, every NaN as
                  0x7FF8000000000000), read as 8 bytes, through 8 tables of 256 random 32-bit words — 24 tables in
                  all, one per (axis, byte) — and the cell's hash is the XOR of its 24 entries; bucket = the hash's low
                  log₂B bits. The 24 × 256 words are drawn from crypto.getRandomValues on every call that has a match.
                  Each match's six per-axis hashes (two shifts × three axes) are computed once, before the eight
                  passes; a pass XORs three of them.
  Why it is better: simple tabulation is 3-independent, so for two distinct cells the chance that they share a bucket
  is EXACTLY 1/B (B divides 2^32) — the expected chain walked per lookup is at most 1 + (m − 1)/B < 1.5 — and it has
  Chernoff-type concentration of the bucket loads [PT12, Theorem 1], which the linear family lacks. Its arithmetic is
  32-bit integer XOR, so no floating-point exactness argument is needed. Every index takes one path, so a far or
  infinite index costs what a near one costs (C-far ≈ C-rand is predicted below).
  Unchanged: the table on typed arrays (B the least power of two ≥ 2m, at least 16; chaining; a stamp per bucket;
  per cell its three indices, last slide run and sum), the equality (componentwise SameValueZero), the cell formula,
  the dedup, the order-free verdict, by-height (kept, per the probe), F-a and F-b, and every prediction Q1′–Q4′.

==== H-PAIRWORK-FIX″ — design F″, pre-registered 2026-10-18 BEFORE it is written (amends F′, as F′ registered) ====
Trigger. F′'s by-height groups the note page's runs in a js/Map keyed by their strings. In the GUI's engine a PDF can
choose strings that share one bucket (above), so one comparison can cost O(r²) string comparisons: the probe's 4 096
keys took 36.6 ms for one set and one get each; by-height makes about five such operations per run. F′ registered
the remedy: "F′ groups the strings in a table of its own, seeded the same way over the strings' UTF-16 code units".
DEVIATION from that remedy, decided now and before any code: F″ groups them by SORTING instead, with no hash at all.
  Why. (1) A seeded hash of variable-length strings needs per-code-unit modular arithmetic for its collision bound
  (a polynomial over a prime field; its bound per pair, length/p, grows with the strings), done in JavaScript doubles
  — about 10–25 ns per code unit — and redone on every comparison, since the seeds are per call; native string
  comparison costs about 1 ns per code unit. (2) A sort is deterministic: its bound holds for every input, with no
  probability and no seed. (3) Sorted stably by height, each string's runs come out in exactly the order F′'s groups
  have, so F″ builds, entry for entry, the arrays F′ builds — F″'s equivalence reduces to F′'s.
Design F″ (F-a, F-b and F′-c's copy-covers? unchanged; by-height and the caps change):
  F″-s  by-height takes the note page's upright runs whose :str is a string, and sorts their indices with a stable
        bottom-up MERGE SORT by (string in UTF-16 code-unit order, cljs.core/compare; then height, <=). A group is a
        maximal block of equal strings in that order (=), so it is an index range [start, end) of the sorted arrays
        hs, xs, ys (heights and origins). A slide run finds its string's group by binary search over the groups'
        strings (compare). prefix-count takes the range: (prefix-count heights from to hs bound), the first index in
        [from, to) whose h/hs exceeds bound — Lemma 1 on a sub-array. kept[2i], kept[2i+1] become absolute indices,
        so the build pass reads hs, xs, ys directly (no second lookup). Runs whose :str is not a string are left out:
        a slide run is matched only when it has a glyph (glyphs is 0 for a non-string), so no lookup is ever made for
        a non-string key, and none of their groups was ever read.
        Cost, for every input: at most n⌈log₂ n⌉ comparisons in the sort; a comparison of x and y reads at most
        3(1 + min(|x|, |y|)) code units (compare is ===, then > and <), charged to the run the merge outputs, so a
        pass costs O(n + T) and the sort O((n + T) log n); the groups' scan O(n + T); a lookup O((1 + |s|) log G).
